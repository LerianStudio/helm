  Bundled MongoDB is ENABLED (Bitnami subchart).
  The internal service will be available at:
    {{ include "product-console.mongodb.host" . }}:27017

  That is also what configmap.MONGO_HOST defaults to, so the console reaches
  the bundled database without naming it. Note the subchart does NOT inherit
  this chart's namespaceOverride: it follows global.namespaceOverride when that
  is set and the release namespace otherwise, while the console always lives in
  '{{ include "product-console.namespace" . }}'.

  {{- if or .Values.secrets.MONGODB_PASS .Values.useExistingSecret }}
  The console uses the MONGODB_PASS you supplied. It must be the password the
  subchart actually runs with (mongodb.auth.rootPassword, or the password in
  the Secret named by mongodb.auth.existingSecret), or every Mongo-backed page
  (product enablement, guided tour) fails on an auth error.
  {{- else if not .Values.mongodb.auth.enabled }}
  The subchart runs with authentication DISABLED, so no password is needed.
  {{- else if eq (include "product-console.namespace" .) (include "product-console.mongodb.namespace" .) }}
  The credential is wired for you. The console reads MONGODB_PASS from key
  'mongodb-root-password' of the Secret the subchart runs with:

    {{ include "product-console.mongodb.secretName" . }}

  There is nothing to copy by hand. Set secrets.MONGODB_PASS only to pin your
  own password instead.
  {{- else }}
  ACTION REQUIRED, or every Mongo-backed page (product enablement, guided tour)
  fails on an auth error. The subchart's password lives in Secret
  '{{ include "product-console.mongodb.secretName" . }}' in namespace
  '{{ include "product-console.mongodb.namespace" . }}', while these pods run in
  '{{ include "product-console.namespace" . }}'. A Secret cannot be read across
  namespaces, so the console cannot pick it up by itself. Either:

    - install into the console's own namespace
      (helm install ... -n {{ include "product-console.namespace" . }}), which
      puts the subchart there too and wires the password automatically; or
    - set BOTH of these to the same value:

        mongodb.auth.rootPassword: "<your password>"
        secrets.MONGODB_PASS:      "<the same password>"
  {{- end }}

{{- else }}

  Bundled MongoDB is DISABLED.
  Configure an external MongoDB connection using one of the following options:

  Option 1 — Full connection string:
    - configmap.MONGODB_URI        (e.g. mongodb://host:27017/dbname)

  Option 2 — Host and port pair:
    - configmap.MONGO_HOST         (hostname)
    - configmap.MONGO_PORT         (default: 27017)

  Both options also require:
    - configmap.MONGODB_DB_NAME    (database name)
    - configmap.MONGODB_USER       (database user)
    - secrets.MONGODB_PASS         (database password)

{{- end }}

================================================================================
  Readiness / MongoDB requirement (read before a fresh install)
================================================================================

  Probe defaults, BOTH on '/api/admin/health/alive' (returns 200 as soon as the
  server answers, no MongoDB dependency; available since app image 1.10.0).

  Readiness does NOT gate on MongoDB, deliberately. '/api/admin/health/readyz'
  returns 200 only once the app has connected to MongoDB, and the image this
  chart pins connects on the first request that needs the database rather than
  at startup. Readiness on readyz therefore DEADLOCKS a fresh pod: not Ready,
  so no traffic, so no connection, so never Ready. Measured on image 1.12.0:
  readyz stays 503 for as long as the pod is left alone, and turns 200 within
  three seconds of the first request to a Mongo-backed route.

  - Running an image that connects EAGERLY at startup? Set
    'readinessProbe.path: /api/admin/health/readyz' to have readiness gate on
    the database again. Scrape readyz either way: it is the honest report of
    whether this pod can serve a Mongo-backed page.
  - Keep liveness on a Mongo-INDEPENDENT endpoint. Do NOT repoint liveness at
    readyz or any Mongo-dependent path, or a disconnected Mongo would
    crash-loop the pod instead of letting it wait for the database.

  See docs/UPGRADE-4.0.1.md for details.
