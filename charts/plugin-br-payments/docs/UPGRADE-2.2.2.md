## Overview

This guide covers the `plugin-br-payments` chart upgrade from `2.2.1` to `2.2.2`. The application version remains `1.2.0`; the chart bump to `2.2.2` is a patch release that introduces documentation improvements, label cleanup, and support for a new optional timeout configuration variable. No breaking changes are included.

This upgrade requires no operator action beyond running the upgrade command. Existing deployments will continue to work without values changes.

## Fixes

### 1. PostgreSQL TLS certificate rotation documentation

The `postgresql.tls` section in `values.yaml` now includes an inline comment explaining the lifecycle and rotation procedure for the auto-generated TLS certificate. The certificate is valid for 365 days and persists across upgrades. To rotate it, operators must delete the `<release>-postgresql-crt` Secret, run `helm upgrade`, then restart the PostgreSQL pods and the application pods.

**After (v2.2.2):**

```yaml
postgresql:
  tls:
    enabled: true
    autoGenerated: true
    # The generated certificate is valid for 365 days and is kept across upgrades. To rotate it, delete the
    # <release>-postgresql-crt Secret, run helm upgrade, then restart the PostgreSQL pods and the app pods.
```

**Operational impact:**

No immediate action is required. This change is purely documentary. If you need to rotate the PostgreSQL TLS certificate in the future, follow the procedure described in the comment:

```bash
kubectl delete secret <release>-postgresql-crt -n <namespace>
helm upgrade <release> oci://ghcr.io/lerianstudio/plugin-br-payments-helm --version 2.2.2 -n <namespace>
kubectl rollout restart statefulset <release>-postgresql -n <namespace>
kubectl rollout restart deployment <release>-plugin-br-payments -n <namespace>
```

> **Note:** The certificate rotation procedure applies only when `postgresql.tls.enabled: true` and `postgresql.tls.autoGenerated: true`. If you provide your own certificate via `postgresql.tls.certificatesSecret`, this comment does not apply.

### 2. AWS IAM Roles Anywhere credential helper comment clarification

The inline comment for `aws.rolesAnywhere.sidecar.image.tag` in `values.yaml` was shortened and clarified. The previous comment included a detailed supply-chain risk explanation and a live registry verification timestamp. The new comment retains the immutable tag pin and the SHA256 digest reference but removes the verbose justification and the timestamp.

**Before (v2.2.1):**

```yaml
aws:
  rolesAnywhere:
    sidecar:
      image:
        repository: public.ecr.aws/rolesanywhere/credential-helper
        # Pinned to an immutable version-platform-timestamp tag, not the
        # rolling `latest-amd64` (Issue #352 review finding, Gandalf
        # 2026-09-10 re-review): this sidecar is a credential-bearing
        # workload, so a mutable tag is a supply-chain risk this chart does
        # not accept for it even though other charts in this repo still use
        # `latest-amd64` for the same image. Verified live against the
        # public ECR registry API on 2026-09-10 — resolves to digest
        # sha256:56b03f3acba0bda06c94189ab62c4a497fd1912f3d08311fb99ab24e4e4c2f84.
        # Bump deliberately; do not revert to `latest-amd64`.
        tag: "1.8.5-amd64-2026.08.24.20.52"
```

**After (v2.2.2):**

```yaml
aws:
  rolesAnywhere:
    sidecar:
      image:
        repository: public.ecr.aws/rolesanywhere/credential-helper
        # Pinned to an immutable version-platform-timestamp tag (digest
        # sha256:56b03f3acba0bda06c94189ab62c4a497fd1912f3d08311fb99ab24e4e4c2f84).
        # Bump deliberately; do not use the rolling `latest-amd64` tag.
        tag: "1.8.5-amd64-2026.08.24.20.52"
```

**Operational impact:**

No configuration change. The image tag and digest remain identical. This is a documentation-only update.

### 3. New REQUEST_TIMEOUT_SEC environment variable support

The `templates/configmap.yaml` template now conditionally renders a `REQUEST_TIMEOUT_SEC` environment variable if the key is present in `app.configmap`. This variable allows operators to configure the HTTP request timeout for the application.

**After (v2.2.2):**

```yaml
{{- if hasKey $cm "REQUEST_TIMEOUT_SEC" }}
REQUEST_TIMEOUT_SEC: {{ index $cm "REQUEST_TIMEOUT_SEC" | quote }}
{{- end }}
```

**Operational impact:**

This is an optional configuration. If you do not set `app.configmap.REQUEST_TIMEOUT_SEC` in your values overlay, the application will use its built-in default timeout. To configure a custom timeout, add the following to your values:

```yaml
app:
  configmap:
    REQUEST_TIMEOUT_SEC: "30"
```

| Flag | Default | Description |
|------|---------|-------------|
| `REQUEST_TIMEOUT_SEC` | application default (not set by chart) | HTTP request timeout in seconds |

> **Note:** The chart does not set a default value for `REQUEST_TIMEOUT_SEC`. If the key is absent from `app.configmap`, the environment variable will not be rendered in the ConfigMap, and the application will use its internal default.

### 4. Control-plane migration Job label cleanup

The `templates/controlplane-migrations.yaml` template was updated to remove the `helm.sh/chart` label from the migration Job pod labels. The label was previously included in the pod template but is not required for the Job's selector or for any operational purpose. The Job pod now carries only the version, managed-by, and part-of labels, matching the label set used by the main application Deployment.

**Before (v2.2.1):**

```yaml
labels:
  helm.sh/chart: {{ include "plugin-br-payments.chart" . }}
  app.kubernetes.io/version: {{ include "plugin-br-payments.versionLabelValue" . }}
  app.kubernetes.io/managed-by: {{ .Release.Service }}
  app.kubernetes.io/part-of: plugin-br-payments
```

**After (v2.2.2):**

```yaml
labels:
  app.kubernetes.io/version: {{ include "plugin-br-payments.versionLabelValue" . }}
  app.kubernetes.io/managed-by: {{ .Release.Service }}
  app.kubernetes.io/part-of: plugin-br-payments
```

**Operational impact:**

No action required. The migration Job will continue to run as before. The label removal does not affect Job execution, pod scheduling, or selector matching.

### 5. Deployment pod label standardization

The `templates/deployment.yaml` template was updated to replace the `include "plugin-br-payments.labels"` helper call with an explicit label set. The pod template now renders only the selector labels (`app.kubernetes.io/name`, `app.kubernetes.io/instance`, `app.kubernetes.io/component`) plus the version, managed-by, and part-of labels. This change removes the `helm.sh/chart` label from the pod template, aligning the Deployment pod labels with the migration Job pod labels.

**Before (v2.2.1):**

```yaml
template:
  metadata:
    labels:
      {{- include "plugin-br-payments.labels" (dict "context" .) | nindent 8 }}
```

**After (v2.2.2):**

```yaml
template:
  metadata:
    labels:
      {{- include "plugin-br-payments.selectorLabels" (dict "context" .) | nindent 8 }}
      app.kubernetes.io/version: {{ include "plugin-br-payments.versionLabelValue" . }}
      app.kubernetes.io/managed-by: {{ .Release.Service }}
      app.kubernetes.io/part-of: plugin-br-payments
```

**Operational impact:**

The Deployment will trigger a rolling restart during the upgrade because the pod template labels have changed. Depending on your replica count and readiness probe configuration, this may cause brief request handling interruptions. Verify all pods are running and healthy after the upgrade:

```bash
kubectl get pods -n <namespace> -l app.kubernetes.io/name=plugin-br-payments
```

> **Important:** The label change does not affect the Deployment's selector. Existing pods will be replaced during the rolling update, but the selector (`app.kubernetes.io/name`, `app.kubernetes.io/instance`, `app.kubernetes.io/component`) remains unchanged.

### 6. Source repository link removal

The `Chart.yaml` sources list and the `templates/NOTES.txt` output no longer include a direct link to the `https://github.com/LerianStudio/plugin-br-payments` application repository. Only the chart source link (`https://github.com/LerianStudio/helm/tree/main/charts/plugin-br-payments`) is retained.

**Before (v2.2.1) — Chart.yaml:**

```yaml
sources:
  - https://github.com/LerianStudio/helm/tree/main/charts/plugin-br-payments
  - https://github.com/LerianStudio/plugin-br-payments
```

**After (v2.2.2) — Chart.yaml:**

```yaml
sources:
  - https://github.com/LerianStudio/helm/tree/main/charts/plugin-br-payments
```

**Before (v2.2.1) — NOTES.txt:**

```
## Source

  - Plugin source:   https://github.com/LerianStudio/plugin-br-payments
  - Chart source:    https://github.com/LerianStudio/helm/tree/main/charts/plugin-br-payments
```

**After (v2.2.2) — NOTES.txt:**

```
## Source

  - Chart source:    https://github.com/LerianStudio/helm/tree/main/charts/plugin-br-payments
```

**Operational impact:**

No configuration change. This is a documentation-only update. The Helm install/upgrade notes will display one fewer source link.

## Configuration Changes

| Setting | v2.2.1 | v2.2.2 |
|---------|--------|--------|
| `app.configmap.REQUEST_TIMEOUT_SEC` | not supported | optional (no default) |

No other configuration values were added, removed, or changed. The `REQUEST_TIMEOUT_SEC` variable is optional; if not set, the chart will not render it in the ConfigMap.

## Migration Steps

1. **(Optional)** If you want to configure a custom HTTP request timeout, add `app.configmap.REQUEST_TIMEOUT_SEC` to your values overlay:

```yaml
app:
  configmap:
    REQUEST_TIMEOUT_SEC: "30"
```

2. Run the upgrade command during a maintenance window (see [Command to upgrade](#command-to-upgrade)).

3. Verify all pods are running and healthy after the upgrade:

```bash
kubectl get pods -n <namespace> -l app.kubernetes.io/name=plugin-br-payments
```

4. **(Optional)** If you configured `REQUEST_TIMEOUT_SEC`, verify the environment variable is present in the running pods:

```bash
kubectl exec -n <namespace> -l app.kubernetes.io/name=plugin-br-payments -- env | grep REQUEST_TIMEOUT_SEC
```

> **Note:** The upgrade will trigger a rolling restart of the application pods due to the pod label change in the Deployment template. Plan the upgrade during a maintenance window if your environment cannot tolerate brief service interruptions.
