## Overview

This guide covers the `plugin-br-payments` chart upgrade from `2.0.0` to `2.0.1`. The application version remains `1.0.2`; the chart bump to `2.0.1` is a patch release that introduces two fixes: the bundled PostgreSQL subchart now enables TLS by default (required by the application in production), and the `ACCESS_CONTROL_ALLOW_ORIGIN` CORS header default was changed from `"*"` to `""` (empty string) to prevent unintended permissive CORS policies.

Existing deployments that rely on the bundled PostgreSQL will automatically gain TLS support. Deployments that previously relied on the `"*"` CORS default must explicitly set `ACCESS_CONTROL_ALLOW_ORIGIN` in their values overlay if they require permissive CORS.

## Fixes

### 1. PostgreSQL TLS configuration

The bundled PostgreSQL subchart now enables TLS by default with auto-generated certificates. The application binary refuses `sslmode=disable` in production environments, so the database must speak TLS. Previously, the chart deployed PostgreSQL without TLS, which caused connection failures when the application enforced SSL mode.

**Before (v2.0.0):**

```yaml
postgresql:
  image:
    repository: bitnamisecure/postgresql
    tag: "latest"
    digest: "sha256:7045d816bdf7e704f0f662fabf243f3c0a975aa380e73e4e881ee94740f60d4f"
  architecture: replication
  replication:
    numSynchronousReplicas: 1
```

**After (v2.0.1):**

```yaml
postgresql:
  image:
    repository: bitnamisecure/postgresql
    tag: "latest"
    digest: "sha256:7045d816bdf7e704f0f662fabf243f3c0a975aa380e73e4e881ee94740f60d4f"
  # The app refuses sslmode=disable in production, so the bundled server must speak TLS.
  tls:
    enabled: true
    autoGenerated: true
  # TLS adds a copy-certs init container; bitnami/os-shell tags are gone, bitnamilegacy serves the pinned tag.
  volumePermissions:
    image:
      repository: bitnamilegacy/os-shell
  architecture: replication
  replication:
    numSynchronousReplicas: 1
```

**Operational impact:**

- The PostgreSQL StatefulSet will add an init container (`copy-certs`) that copies TLS certificates from a secret to the data volume. This init container uses the `bitnamilegacy/os-shell` image because the `bitnami/os-shell` tags were removed from the upstream registry.
- The PostgreSQL pods will restart during the upgrade to apply the TLS configuration.
- The application pods will automatically connect via TLS once PostgreSQL is ready. No application configuration changes are required if you use the default connection string template.
- If you override `postgresql.primary.extraEnvVars` or `postgresql.auth.postgresPassword` in your values overlay, verify that your connection string includes `sslmode=require` or `sslmode=verify-ca`.

> **Important:** If you use an external PostgreSQL instance (`postgresql.external: true`), this change does not affect you. Ensure your external database already supports TLS connections, as the application will attempt to connect with SSL mode enabled.

> **Note:** The auto-generated TLS certificates are self-signed and stored in a Kubernetes secret. If you require CA-signed certificates, set `postgresql.tls.autoGenerated: false` and provide your own certificates via `postgresql.tls.certificatesSecret`.

### 2. CORS default value security hardening

The default value for `ACCESS_CONTROL_ALLOW_ORIGIN` was changed from `"*"` (allow all origins) to `""` (empty string, no CORS headers). The previous default allowed any origin to make cross-origin requests to the API, which is a security risk in production environments.

**Before (v2.0.0):**

```yaml
ACCESS_CONTROL_ALLOW_ORIGIN: {{ include "plugin-br-payments.cfg" (dict "root" $ "key" "ACCESS_CONTROL_ALLOW_ORIGIN" "default" "*") | quote }}
```

**After (v2.0.1):**

```yaml
ACCESS_CONTROL_ALLOW_ORIGIN: {{ include "plugin-br-payments.cfg" (dict "root" $ "key" "ACCESS_CONTROL_ALLOW_ORIGIN" "default" "") | quote }}
```

**Operational impact:**

- Deployments that did not explicitly set `app.configmap.ACCESS_CONTROL_ALLOW_ORIGIN` in their values overlay will now render an empty `ACCESS_CONTROL_ALLOW_ORIGIN` environment variable.
- The application will not send `Access-Control-Allow-Origin` response headers when the value is empty, effectively disabling CORS.
- Browser-based clients that make cross-origin requests to the API will receive CORS errors unless you explicitly configure the allowed origins.

**Migration options:**

#### Option 1: Restore permissive CORS (not recommended for production)

If your deployment requires the previous `"*"` behavior, add the following to your values overlay:

```yaml
app:
  configmap:
    ACCESS_CONTROL_ALLOW_ORIGIN: "*"
```

> **Warning:** Allowing all origins (`"*"`) is a security risk. Use this option only in development or testing environments.

#### Option 2: Configure specific allowed origins (recommended)

Set `ACCESS_CONTROL_ALLOW_ORIGIN` to a comma-separated list of allowed origins:

```yaml
app:
  configmap:
    ACCESS_CONTROL_ALLOW_ORIGIN: "https://example.com,https://app.example.com"
```

> **Note:** The application expects a comma-separated string. Consult the application documentation for the exact format if you need to allow multiple origins.

#### Option 3: Disable CORS (default)

If your API is not accessed by browser-based clients or if CORS is handled by an upstream proxy (e.g., an ingress controller or API gateway), you can leave `ACCESS_CONTROL_ALLOW_ORIGIN` empty (the new default). No action is required.

## Configuration Changes

| Setting | v2.0.0 | v2.0.1 |
|---------|--------|--------|
| `postgresql.tls.enabled` | not set (false) | `true` |
| `postgresql.tls.autoGenerated` | not set | `true` |
| `postgresql.volumePermissions.image.repository` | not set (default `bitnami/os-shell`) | `bitnamilegacy/os-shell` |
| `app.configmap.ACCESS_CONTROL_ALLOW_ORIGIN` (default) | `"*"` | `""` |

No other configuration values were added, removed, or changed.

## Migration Steps

1. **(Required if you rely on CORS)** If your deployment serves browser-based clients that make cross-origin requests, add an explicit `ACCESS_CONTROL_ALLOW_ORIGIN` value to your values overlay. See [Option 2: Configure specific allowed origins](#option-2-configure-specific-allowed-origins-recommended) for the recommended approach.

2. **(Optional)** If you use an external PostgreSQL instance, verify that it supports TLS connections and that your connection string includes `sslmode=require` or `sslmode=verify-ca`.

3. **(Optional)** If you override `postgresql.tls` settings in your values overlay, ensure your configuration is compatible with the new defaults. The chart now expects `postgresql.tls.enabled: true` and `postgresql.tls.autoGenerated: true` for the bundled PostgreSQL.

4. Preview the rendered diff with the helm-diff plugin (see [Preview changes before upgrading](#preview-changes-before-upgrading)).

5. Run the upgrade command during a maintenance window (see [Command to upgrade](#command-to-upgrade)).

6. Verify all pods are running and healthy after the upgrade:

```bash
kubectl get pods -n <namespace>
```

7. If the PostgreSQL StatefulSet is managed by this chart, confirm the TLS configuration is active:

```bash
kubectl get statefulset -n <namespace> -l app.kubernetes.io/name=postgresql -o jsonpath='{.items[0].spec.template.spec.initContainers[?(@.name=="copy-certs")].name}'
```

Expected output:

```
copy-certs
```

8. Check the application logs to confirm successful database connections with TLS:

```bash
kubectl logs -n <namespace> -l app.kubernetes.io/name=plugin-br-payments-helm --tail=50 | grep -i ssl
```

9. **(If you configured CORS)** Test cross-origin requests from your browser-based client to verify the `Access-Control-Allow-Origin` header is present in API responses:

```bash
curl -H "Origin: https://example.com" -I https://<your-api-endpoint>/health
```

Expected response headers should include:

```
Access-Control-Allow-Origin: https://example.com
```

> **Important:** If the PostgreSQL pods fail to start after the upgrade with TLS-related errors, verify that the `copy-certs` init container completed successfully. Check the init container logs:

```bash
kubectl logs -n <namespace> <postgresql-pod-name> -c copy-certs
```
